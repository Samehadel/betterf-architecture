# Frontend i18n Guide

> **Library:** `@jsverse/transloco` · **Locales:** `en` (default), `ar` · **Story:** KAN-72

---

## How It Works

Transloco loads JSON translation files at runtime from `/i18n/{lang}.json`. The active language is managed by `LocaleService`, which:

1. Reads the preferred locale from `localStorage` (`preferred-locale` key)
2. Falls back to the browser's `navigator.language` (first segment only, e.g. `ar-EG` → `ar`)
3. Falls back to `en` if neither is supported
4. Sets `dir` and `lang` attributes on `<html>` and calls `TranslocoService.setActiveLang()`

Translation files live in `frontend/public/i18n/`. Because the Angular build serves `public/` at the root, these files are available at `/i18n/en.json` and `/i18n/ar.json` without any special asset configuration.

---

## Translation Key Naming Convention

Keys follow the **`{feature}.{component}.{element}`** pattern — matching the project's domain-driven folder structure.

```
{feature}    →  auth | queue | dashboard | customer | business | shared
{component}  →  page, panel, entry, row, form, etc.
{element}    →  title, submit, empty, errors.invalidCredentials, etc.
```

### Examples

```json
{
  "auth.login.title": "Welcome Back",
  "auth.login.submit": "Sign In",
  "auth.login.errors.invalidCredentials": "Invalid email or password",

  "queue.panel.callNext": "Call Next",
  "queue.panel.status.active": "Active",

  "shared.actions.save": "Save",
  "shared.status.loading": "Loading..."
}
```

> **Note:** The JSON files use nested objects (not flat dot-notation keys). Transloco resolves nested paths automatically. Keep nesting to a maximum of **3 levels deep** (`feature → component → element`). The `errors` sub-object is a permitted 4th level for grouped error messages only.

## Using Translations in Components

### In smart (page-level) components

Use `TranslocoService` with `toSignal()` to consume translations as signals. Never use the pipe in templates — signals are the project standard.

```typescript
import { Component, inject } from '@angular/core';
import { TranslocoService } from '@jsverse/transloco';
import { toSignal } from '@angular/core/rxjs-interop';

@Component({ ... })
export class LoginPageComponent {
  private readonly transloco = inject(TranslocoService);

  // Reactive: re-emits whenever the active language changes
  readonly t = toSignal(this.transloco.selectTranslation('auth.login'));
}
```

```html
<h1>{{ t()?.['title'] }}</h1>
<button>{{ t()?.['submit'] }}</button>
```

For a single key:

```typescript
readonly pageTitle = toSignal(this.transloco.selectTranslate('auth.login.title'));
```

```html
<h1>{{ pageTitle() }}</h1>
```

### In presentational components

Presentational components must not inject services. Pass already-resolved strings via `input()`:

```typescript
@Component({ ... })
export class LoginFormComponent {
  readonly submitLabel = input.required<string>();
}
```

The smart parent resolves the translation and passes the string down.

## RTL Support

`LocaleService` sets `dir="rtl"` on `<html>` when the active locale is Arabic, and `dir="ltr"` otherwise. Tailwind v3 has built-in `rtl:` and `ltr:` variants that activate based on this attribute — **no plugin is required**.

### Rule

Write new components with logical (bidirectional) styles from the start. Do **not** retroactively convert existing components unless they are being modified for another reason.

```html
<!-- Avoid — physical direction hardcoded -->
<div class="ml-4 text-left pl-2">...</div>

<!-- Correct — logical variants -->
<div class="ltr:ml-4 rtl:mr-4 ltr:text-left rtl:text-right ltr:pl-2 rtl:pr-2">...</div>
```

Common mappings:

| Physical (avoid) | Logical (use) |
|---|---|
| `ml-*` | `ltr:ml-* rtl:mr-*` |
| `mr-*` | `ltr:mr-* rtl:ml-*` |
| `pl-*` | `ltr:pl-* rtl:pr-*` |
| `pr-*` | `ltr:pr-* rtl:pl-*` |
| `text-left` | `ltr:text-left rtl:text-right` |
| `text-right` | `ltr:text-right rtl:text-left` |
| `left-*` (positioning) | `ltr:left-* rtl:right-*` |
| `right-*` (positioning) | `ltr:right-* rtl:left-*` |

## Adding a New Language

1. Create `frontend/public/i18n/{lang}.json` with all keys from `en.json` translated.
2. Add the lang code to `availableLangs` in `app.config.ts` (`provideTransloco`).
3. Add the type to `SupportedLocale` in `locale.service.ts`.
4. Update `LocaleService.SUPPORTED_LOCALES` array.
5. Set `document.documentElement.dir` logic in `LocaleService` if the new language is RTL (add it to the `locale === 'ar'` check or extract to a set).

---

## Locale Persistence

The user's preferred locale is stored in `localStorage` under the key `preferred-locale`. Backend user profile persistence is deferred — `localStorage` is the single source of truth for now.

---

## What NOT to Do

- **Never use the `| transloco` pipe in templates.** Use `toSignal(transloco.selectTranslate(...))` in the component and read the signal in the template.
- **Never inject `TranslocoService` into presentational components.** Resolve translations in the smart parent and pass strings via `input()`.
- **Never add a key to only one translation file.** Both `en.json` and `ar.json` must be updated together.
- **Never nest keys deeper than 3 levels** (4 levels only for `errors` sub-objects).
