# Internationalization — Reference Patterns

> Reusable reference, not an accepted BetterF technology or product decision. See [documentation status](../../README.md#documentation-status). Examples are illustrative; validate framework APIs against the versions selected for implementation.

## Locale decisions

Supported languages, default locale, fallback order, persistence, and right-to-left support must come from BetterF requirements. No language set or locale service is assumed to exist.

When localization is needed, keep user-facing strings in translation resources, set the document language and direction appropriately, and format dates/numbers using the active locale.

## Translation organization

Group keys by feature, component, and purpose:

```text
{feature}.{component}.{element}
shared.actions.save
shared.status.loading
```

Illustrative nested resource:

```json
{
  "shared": {
    "actions": { "save": "Save" },
    "status": { "loading": "Loading..." }
  }
}
```

Keep keys consistent across supported locales and define behavior for missing translations.

## Optional Angular integration

Transloco is one possible runtime translation library. If selected, configure its loader and locale support in the application. `toSignal()` can expose observable translations to a signal-based component; reusable children can receive translated labels through inputs.

Select library versions, resource paths, pipe/signal conventions, and locale persistence explicitly. This guide does not require an existing `LocaleService` or storage key.

## Bidirectional layout

Use logical spacing/alignment where possible and verify both layout directions when required. Test navigation, icons, numbers, forms, text expansion, and focus behavior. Do not assume every icon should mirror.

## Adding a locale

Add translations, register the locale in the selected implementation, configure its direction and formatting, and test fallback/persistence behavior. Keep supported resources complete in the same change.
